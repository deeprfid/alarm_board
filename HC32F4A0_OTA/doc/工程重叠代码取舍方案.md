# App / Driver_lib / Boot 重叠代码取舍方案

> 日期：2026-08-21 | 基于实际工程扫描

### 4. 头文件双份

- driver_lib/json-parser.h vs projects/jsonlib/json-parser.h

## 二、取舍原则

1. **单一来源（Single Source of Truth）**：每个文件只在一处物理存在，其他工程通过路径引用
2. **分层归属**：LL 驱动/平台层 → driver 工程；业务/中间件 → app 工程
3. **编译期归属**：谁编译谁所有，未编译副本是死文件

## 三、具体取舍方案

### 方案 T1：按工程归属，消除物理重复（推荐）

| 文件 | 归属 | 处理 |
|---|---|---|
| hc32_ll_efm.c/.h | driver（唯一） | app/boot 改为引用 driver 的（include 路径指过去）或从 lib 链接 |
| system_hc32f4a0.c | driver（唯一） | app/boot 用 RTE 版，删除 projects/cmsis 副本 |
| json-parser 等 jsonlib | **app**（唯一） | driver 目录删除（app 已编译）；driver_lib 的头文件指向 app 或删除 |
| http_parser.c | app/middleware（唯一） | driver/jsonlib 副本删除 |
| qspi_flash.c/.h | driver→lib（唯一） | app 只留 driver_lib/qspi_flash.h 引用；删 app 内副本（若有） |
| driver_lib/inc/*.h | driver（唯一） | 保持；driver_lib 是发布产物 |

### 方案 T2：建立公共模块目录（更彻底）

创建 `common/` 目录（三工程共享）：
```
common/
  ll/          (hc32_ll_*.c/.h —— 从 driver 提取，app/boot 引用)
  json/        (json-parser 或统一后的 cJSON —— 唯一)
  net/         (wizchip/socket —— 唯一)
  qspi/        (qspi_flash —— 唯一)
```
三个工程 uvprojx 的 include 路径统一指向 common/，不再各自拷贝。

## 四、执行顺序建议

1. **先统一 json**（上一步已开始）：json-parser 唯一化 → 后续 cJSON 统一
2. **hc32_ll_efm 唯一化**：driver 是源，app/boot 改引用（或链接 lib 符号）
3. **system_hc32f4a0 唯一化**：全用 RTE 版，删 projects/cmsis 副本
4. **http_parser 唯一化**：删 driver/jsonlib 副本
5. **qspi_flash 唯一化**：driver 源码 → lib，app 只引用头
6. **（远期）common/ 目录**：三工程共享源码

## 五、风险与注意

- 每次唯一化后**必须 Rebuild 对应工程**验证（改 include 路径可能引入编译错误）
- driver_lib 是预编译 lib：app 依赖它的符号（hc32_ll_*），**不能直接删 driver_lib/inc**（app include 用它）
- boot 独立编译：改 boot 的 LL 引用要重编 boot 并回归 OTA commit/swap
- jsonlib 双目录：确认 app 编译用哪个（uvprojx FilePath 是 ..\jsonlib\ = app/projects/jsonlib）

## 六、结论

**推荐 T1（按工程归属消除物理重复）+ 逐步 T2（common/ 目录）**：
- 短期：删重复副本 + 统一 include 路径（零功能变化）
- 中期：json 统一 + LL 唯一化
- 长期：common/ 共享模块目录

核心目标：**每个源文件物理唯一，三工程通过路径引用**——消灭改一处不同步的隐患。
