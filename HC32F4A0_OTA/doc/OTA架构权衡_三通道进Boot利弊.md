# OTA 架构权衡：三通道从 App 移入 Boot 的利弊分析

> 日期：2026-08-21 | 背景：局域网明文 HTTP（无 TLS），暂不考虑云端升级
> 前提数据（实测/工程文件统计）：
> - Boot 当前 ROM 18.9KB / 分区 64KB（余量 ~45KB）；Boot 为裸机 main 循环（无 RTOS）
> - App 总 ROM 389.6KB / 上限 896KB
> - USB 栈 usb_lib：84 文件 / 779KB 源码（含 RTX5 依赖）
> - W5100S 网络：socket.c 892 行 + wizchip_conf.c 850 行 + w5100s.c 463 行 + DHCP/DNS
> - mbedTLS：局域网明文场景只需 md+sha256（HMAC 验签 ~15KB）；TLS 栈（ssl_*）可全裁
> - App 业务也引用 mbedTLS（httpapi/mqtt 可配 TLS，gIsTlsConn），但 OTA 下载走 http:// 明文

---

## 三种方案概览

| | 方案 0（现状） | 方案 A（三通道全进 Boot） | 方案 B（串口进 Boot，USB/HTTP 留 App） |
|---|---|---|---|
| 下载执行位置 | App | Boot | 串口→Boot；USB/HTTP→App |
| App 纯业务 | ✗ 含 OTA | ✓ 最纯 | 半纯（剩 USB/HTTP） |
| Boot 体积 | 19KB | ~85-95KB（超 64KB 分区） | ~23KB（不超） |
| 需要扩 Boot 分区 | 否 | 是（64→128KB+） | 否 |
| 变砖兜底能力 | 弱（App 坏则无法下载） | 最强 | 强（Boot 串口救砖） |
| 开发工作量 | 基准 | 极大（裸机重写 USB/网络驱动+状态机） | 中（Boot 加串口通道 ~4KB） |
| 发送端脚本改造 | 基准 | 全改（时序/握手） | 仅串口脚本微调 |

---

## 方案 A（三通道全进 Boot）利弊

### 优点
1. App 彻底纯业务：OTA 状态机/通道/验签全移出，代码和 RAM 大幅简化
2. 下载环境最干净：Boot 阶段无 RTOS 业务线程，无通道竞争/互斥问题
   （v9.81 踩过的坑：send_func 抢 USB1、ACK 栈缓冲、通道锁——从根上消失）
3. 恢复能力最强：App 崩溃/被刷坏也能通过 Boot 任一通道下载恢复
4. 安全边界清晰：验签在可信 Boot 环境，App 无权篡改升级流程

### 缺点 / 代价
1. Boot 分区不够：USB 栈（84 文件）＋ W5100S 网络栈 ＋ mbedTLS md ≈ 85-95KB > 64KB
   → 必须扩到 128KB 以上，App 上限 896KB→832KB（当前 390KB 够，但未来受限）
2. Boot 无 RTOS，驱动重写难度大：
   - USB CDC 依赖中断/RTX5/内存池，裸机重写事件模型工作量大且易错
   - 网络 socket 状态机（DHCP 可裁、静态 IP）裸机实现复杂
   - 下载超时/断线恢复需要 Boot 级看门狗+状态机（新增变砖风险点）
3. Boot 复杂度↑ = 变砖风险↑：Boot 是最后防线，塞入 100KB 驱动代码后，
   Boot 自身 bug 将导致永久变砖（无处可救）
4. 双份驱动维护：USB/网络驱动在 App 和 Boot 各一份，升级需同步两处
5. FlashDB/KV 依赖：进度/标志现用 FlashDB KV（Boot 无），需迁到 Boot 可读的
   裸存储（标志页/专用扇区），断点续传实现成本增加
6. 发送端脚本全部改造：设备 reboot 进 Boot 后有下载窗口期，PC 必须在
   5-10s 内发起连接；串口/USB/HTTP 三个脚本的握手逻辑都要改

---

## 方案 B（串口进 Boot，USB/HTTP 留 App）利弊

### 优点
1. 救砖兜底：Boot 串口下载 = 任何情况下（App 坏/网络坏/USB 坏）都能恢复，
   这是 OTA 架构最重要的安全网
2. Boot 体积可控：+4KB（纯 UART 帧协议，v9.81 串口代码裁剪），23KB < 64KB 不扩分区
3. Boot 复杂度几乎不增：串口是同步简单协议，裸机可写，风险最低
4. App 瘦身部分达成：移除串口通道 + 相关状态机（~15-20KB）
5. USB/HTTP 维持现状：业务在线下载体验不变，发送端脚本基本不改

### 缺点 / 代价
1. App 仍含 USB/HTTP OTA：不是纯业务，瘦身不彻底
2. Boot 串口与 App 串口复用冲突：Boot 下载用 USART1（PB0/PB1），
   需与 App 命令口时序协调（Boot 阶段专用，App 启动后交还）
3. 两套下载路径：串口走 Boot，USB/HTTP 走 App——逻辑双轨，维护需注意
4. 断点续传跨 Boot/App 语义：进度 KV 在 FlashDB（App），Boot 串口下载
   需要 Boot 也能读写进度（或简化：Boot 串口总是全量重传）

---

## 方案 0（现状）利弊

### 优点
1. 已验证可用：v9.81o/p 三通道真机闭环，稳定性已实测
2. Boot 最小：19KB 只做 commit/swap/confirm，变砖风险最低
3. 下载期间业务在线：HTTP/USB 通道在 App 运行时可用（用户体验）
4. 发送端脚本成熟：无需改动

### 缺点 / 代价
1. App 不纯：OTA 代码与业务共存，代码量和 RAM 占用增加
2. 下载环境有竞争：需通道互斥（已有 ota_channel_*），踩过的坑靠补丁维护
3. 恢复能力弱：App 损坏时无法主动下载新固件（只能 commit 已暂存的包）
   ——若暂存区也空/坏，设备只能 JTAG 救

---

## 综合建议（中立）

| 决策维度 | 推荐 | 理由 |
|---|---|---|
| 若追求 App 纯业务 | 方案 A（接受扩分区+Boot 复杂化） | 但需评估 Boot 变砖风险的承受度 |
| 若追求最低风险 + 救砖兜底 | 方案 B | 性价比最高，Boot 只加 4KB 串口 |
| 若追求不动现有稳定代码 | 方案 0 | 已真机验证，仅优化可继续 |
| 折中最优 | 方案 B | 分通道按价值迁移：串口（救砖）进 Boot，USB/HTTP 留 App |

### 关键判断依据
1. Boot 是最后防线，越简单越安全——嵌入式 OTA 的铁律
2. USB/网络驱动在无 RTOS 的 Boot 里重写，风险远大于收益（尤其 USB 84 文件）
3. 救砖能力是硬需求：生产环境 App 被刷坏是常态，Boot 串口兜底价值最高
4. 局域网明文 HTTP 大幅降低网络栈成本（无 TLS），但 USB 栈成本不变

> 结论：三通道全移 Boot 收益主要在 App 纯净，但代价是 Boot 复杂化+变砖风险；
> 串口进 Boot 是以小博大的折中，兼顾救砖兜底与风险可控。
