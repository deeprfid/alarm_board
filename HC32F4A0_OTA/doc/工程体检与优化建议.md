## 二、RAM 管理问题（用户重点关注，实锤严重）

### 现状：三套内存机制并存，互相混乱

**机制 1：标准 malloc（ARM 堆）**
- startup.s: Heap_Size = 8KB（0x2000）→ 太小
- main.c: heap_base 动态（Image$$RW_IRAM1$$ZI$$Limit），heap_top = 0x20060000（512KB 末端）
- 即：堆起点=静态区末尾，终点=SRAM 末端——heap 与 RW 静态区共用 512KB 空间（startup 的 Heap_Size 8KB 实际没用上）

**机制 2：mp_pool（自研内存池，jsonlib/mp_pool.c）**
- mp_malloc()：自定义链表式分配（start[0] 标记 + 2B 长度头）
- **mp_free() 是空实现！**（只有注释掉的 printf）→ mp_malloc 的内存永不释放
- mp_resetpool() 整个清空——一锅端

**机制 3：malloc_hexp/free_hexp（记账包装，driver common.c）**
- malloc_hexp = malloc + 记账到 gMItems[80]（只记不管理）
- free_hexp = 查 gMItems + free
- **gMItems 只有 80 项，超限会越界写 gMItems[80]（数组越界！）**
- get_left_heap_size 用硬编码 0x20000000-0x20060000 估算（与 main.c 动态 heap_base 不一致！）

### 具体问题清单

| # | 问题 | 位置 | 风险 |
|---|---|---|---|
| M1 | mp_free 空实现，内存只 alloc 不 free | mp_pool.c | 长期运行内存耗尽 |
| M2 | gMItems[80] 无越界检查，>80 次未 free 的 malloc_hexp 越界写 | common.c:410 | 内存破坏/崩溃 |
| M3 | 三套分配器并存（malloc/mp_malloc/malloc_hexp），分配释放不配对 | 全局 | 无法追踪泄漏 |
| M4 | heap_base 动态 vs get_left_heap_size 硬编码 0x20000000，估算失真 | common.c:393 | 误导调试 |
| M5 | 静态大缓冲与堆共用 512KB，无统一预算 | sct | 静态涨则堆缩 |
| M6 | mbedtls 用 calloc_hexp 替换默认 calloc/free | http_callback.c:260 | TLS 内存也走记账，泄露难查 |
| M7 | TagBuffer.c / List.c 用原生 malloc/free，与 hexp 混用 | 多处 | 不一致 |

### RAM 优化方案（推荐）

**方案 R1（推荐）：统一到一个分配器 + 静态预算表**
1. 保留 ARM 堆（malloc 稳定），删掉 mp_pool 和 malloc_hexp 记账层，全部改标准 malloc/free + 统一封装 mem_alloc/mem_free
2. 静态缓冲（TagBuffer、MQTT、USB 端点）列出静态预算表（每个缓冲大小/用途），与堆一起做 RAM 预算
3. 启动时 get_left_heap_size() 改为读 __initial_sp - heap_base - 静态预算（动态算，去掉硬编码）

**方案 R2（激进）：静态分配为主 + 固定池**
- 所有固定大小缓冲改静态数组（编译期确定），只留可变长度走堆
- 引入 mem_stats() 打印堆峰值/碎片，上线后监控

**方案 R3（RTOS 原生）**：用 RTX5 的 osMemoryPool 替代自研池（现成、带超时、可统计）

## 三、架构分层问题（App 耦合严重）

### 现状：无清晰分层，全局变量满天飞
- 全局变量散落：gSocketConnected、gSerIp、gRdrErr、gRtSetting、gPRdrStaSet、gCurWorkMode...
- 模块互相 include 头文件直接用对方全局（app_conf.h 声明了一堆 extern）
- user_main.c 同时管：初始化、线程创建、业务主循环、OTA 启动

### 优化方案（引入分层理念）

目标分层：
  应用层 (app/)
    business: reader_msg/EPC_TagStorage/...
    protocols: modbus/http/mqtt/ota
    services: flashdb/memory/event_mq
  平台抽象层 (platform/)
    hal: uart/usb/net/gpio/timer 接口(头文件)
    rtos: 线程/消息/锁 封装
  驱动层 (driver_lib/)
    hc32_ll_* + wizchip + usb + json

1. 每个模块只通过 .h 暴露接口，内部 static 化——先做头文件 API 清理
2. 全局状态收敛：gRdrErr/gCurWorkMode 等收进 app_context_t 单例结构体，按模块分组
3. 初始化注册表：user_main 的一长串 init 改为模块自注册 + 按依赖排序启动（类似 RTOS 的 board_init 表）

## 四、具体重构点（按优先级）

### P0 内存安全（先修，影响稳定性）
- [M1] mp_free 实现（或删 mp_pool 统一 malloc）
- [M2] gMItems 越界防护（加边界检查或改链表）
- [M3] 统一分配器入口

### P1 架构清理
- [A1] modbus_mode.c 2484 行拆表驱动：寄存器表（regid/access/validator）+ 统一分发（删 20+ 个 *_resp 重复）
- [A2] http_callback.c 1017 行拆模块：http_parser 封装 / command 分发 / mbedtls 生命周期
- [A3] user_main.c 拆：init_sequence + main_loop + 线程表
- [A4] 魔法数清理：配置项全走 app_conf.h 或 config 结构体

### P2 死代码/冗余（体积）
- [D1] yyjson.c 9737 行编译但从未链接（map 确认）→ 从工程移除（省编译时间；若需保留移出工程目录）
- [D2] driver 的 jsonlib 与 app 的 json-parser 并存 → 二选一
- [D3] hc32_ll_efm.c 在 app 和 boot 各一份 → 提取公共 LL 目录
- [D4] driver/user 的 custom_ee_commond.c、usr_mod.c 等检查是否死代码

### P3 编程理念引入（可选，长期）
- [N1] 状态机框架：OTA 升级/连接管理改有限状态机（现用散落的 if/flag）
- [N2] 表驱动：modbus 寄存器、命令分发（cmd_table）、协议头解析
- [N3] 单元测试：协议解析（modbus/crc/json）抽纯函数 + PC 侧测试
- [N4] 静态分析：引入 cppcheck/misra 规则，CI 钩子
- [N5] 配置化：客户定制项（Custom_By_*）改运行时配置而非编译宏

## 六、执行路线建议

**阶段 1（1-2 周，安全优先）**：M1/M2/M3 内存修复 + D1/D2 死代码清理 + B1 LL 共享
**阶段 2（2-4 周，架构）**：A1/A2/A3 大文件拆分 + 全局变量收敛 + API 头文件清理
**阶段 3（持续）**：N1-N5 新理念引入（状态机/表驱动/测试/静态分析）

> 每个阶段保持编译通过 + 真机回归门槛；OTA 三通道是回归基准。
