## 0. 结论(先看这个)

| 事实 | 依据 |
| --- | --- |
| **模块在 460800、驱动"在初始化时就设成 460800" → 通信正常** ✓ | 现场实测：本版(上电即 460800、不做运行时切换、不发任何命令)可用 |
| **模块在 460800、驱动"先按 256000 初始化、运行时再切到 460800" → 不通** ✗ | 现场实测：多版自适应代码均失败 |
| 因此本产品口径：**雷达口固定 460800（初始化时设定）**，不做运行时波特率切换 | `RADAR_BAUD_INIT_FIXED = 460800UL` |
| 探测/上电流程**禁止**发送 `0x00FF`/`0x00FE`(使能/关闭配置) | 现场要求：`0x00FF` 会让模块进配置态并停止上报，一旦 `0x00FE` 丢失模块就"哑" |

**一句话：问题不在波特率数值、不在模块、不在接线，而在"运行时改波特率"这条路径。**

## 5. 追加：USART 时钟分频 / 过采样到底怎么选（2026-09-14）

> 起因：SDK 例程里 115200 用 `USART_CLK_DIV64`、时钟同步模式 9600 也用 `USART_CLK_DIV64`，
> 那我们雷达口用的 `USART_CLK_DIV4` 是不是选错了？

### 5.1 规则（全部来自 DDL 源码，不是推测）

- 分频只有 4 档：`PR.PSC` 是 **2 位**，**实际分频 = 4^PSC** → 只有 /1、/4、/16、/64（`hc32_ll_usart.c:581`）。
- DDL 计算用的 C = `SystemCoreClock >> PCLK1S` / 分频 = **100MHz / 分频**（本工程 HCLK=200MHz、PCLK1=DIV2；
  `USART_GetBusClockFreq()` 对**所有** USART 一律取 PCLK1 —— 这也是 460800 能通的旁证）。
- BRR：整数在 `[15:8]`（**8 位，最大 255**）、小数在 `[6:0]`（7 位，最大 127）。
  `DIV_Integer = C/(B*8*(2-OVER8)) - 1` 必须 ≤ 255，否则 `USART_SetBaudrate()` 返回错误**且根本不写 BRR**。
  于是有两条边界：**C ≥ 8*(2-OVER8)*B_max**（最高档能表示）、**C ≤ 8*(2-OVER8)*256*B_min**（最低档能表示）。

### 5.2 协议表 6 的 8 档逐个算（C × 过采样，✔ = 全部可表示）

| C（分频） | 8 倍过采样（OVER8=1） | 16 倍过采样（OVER8=0） |
| --- | --- | --- |
| 100MHz（DIV1） | 仅 57600~460800，9600/19200/38400 ✗ | 仅 38400~460800 ✗ |
| **25MHz（DIV4）** | 19200~460800 ✔，**9600 ✗**（需 324>255） | **9600~460800 全 ✔**（最大误差 0.217%） |
| 6.25MHz（DIV16） | **9600~460800 全 ✔**（最大误差 0.217%） | 9600~256000 ✔，**460800 ✗** |
| 1.5625MHz（DIV64） | 9600~115200 ✔，**230400/256000/460800 ✗** | 仅 9600~38400 ✗ |

### 5.3 结论

1. **SDK 例程的 `USART_CLK_DIV64` 不是"标准答案"**：那些例程整份只用一个波特率，选大分频是为了把**那一个**低波特率的
   误差做到最小（115200@DIV64+8 倍误差仅 0.003%）。我们要求 9600~460800 **8 档全兼容**，DIV64 连 230400 都算不出来。
2. **只要 460800 一档 → `DIV4` + 8 倍过采样**，就是 `b6d8210` 现场确认可用的组合。
3. **要 9600~460800 全档 → 数学上只有两种组合**：`DIV4 + 16 倍`（5147bd6）或 `DIV16 + 8 倍`（本次试验版）。
   两者误差都 ≤0.22%，都能收到；差别只在"离已验证组合多远"。
4. 所以：**分频本身不是 9600 收不到的原因**（16 倍那版已经算对了，见 5.4），9600 的问题在别处（见 §4 第 1 条的三项诊断）。

### 5.4 顺带确认的两件事

- **回读 `g_radar_brr = 0xA1FF` 是对的**：DDL 算出 `0xA17F`（整数 161、小数 127），而 BRR 的 **bit7 不在 DDL 的写掩码里**
  （`MODIFY_REG32(BRR, 0xFF00|0x007F, …)`），复位值 bit7=1 一直留着 → 读出来就是 `0xA1FF`。
  即：**初始化路径确实把 9600 写进去了**（本次 DIV16+8 倍版对应 `0x507F`，回读应为 `0x50FF`）。
- 9600 的真实波特率：按 DDL 公式 = 9607Hz（+0.08%），按"整数 + 小数/128"模型 = 9589Hz（−0.12%），
  **两种模型都在 0.2% 内 → 不可能因为波特率误差收不到帧**。

## 6. 结论（2026-09-14）：放弃 9600 / 低波特率 / 运行时换档，产品口径回到"固定 460800"

**决定**：不再追 9600 与运行时换档。雷达口恢复并冻结为现场确认可用的配置 ——
`RADAR_BAUD_INIT_FIXED = 460800`、分频 `DIV4` + 8 倍过采样、上电走初始化路径设定、**不做运行时切换、上电不发任何命令**；
本次为调试新增的全部诊断变量（`g_radar_brr` / `rx_bytes` / `pin_low` / `dma_left` / `rx_err` / `low_pct` / `bps` / `dma_fill` / `poll_hz` / `to_hz` / `win_hz` 与 1 秒窗口统计）**全部删除**（即回退到 `b6d8210` 的 `radar_port.c/.h`、`radar_cfg.h`）。

**为什么放弃（按证据）**

| 证据 | 结论 |
| --- | --- |
| 模块 460800 + 驱动初始化 460800（DIV4 + 8 倍）→ 通信正常 | 初始化路径设定波特率没问题 |
| 分频换了三档（DIV4+16 倍 / DIV16+8 倍 / DIV64+8 倍）都算得出 9600，误差 ≤0.22% | **分频/BRR 不是原因** |
| 回读 `g_radar_brr = 0xA1FF`（DIV4+16 倍）、`0x50FF`（DIV16+8 倍）与理论值一致（bit7 是 DDL 写掩码外的残留位） | 9600 的波特率寄存器**写得完全正确** |
| 9600 下 `s_reports` 一直为 0 | 收不到合法帧 |
| **运行中 `g_radar_rx_bytes` 恒为 0；Keil 里暂停再恢复就变成 `0x100`（正好一个 256B 窗口）** | CPU 停住（外设照跑）时 DMA 能搬满整窗 → **线上确有数据**；问题属于"运行时接收链被打断"一类，与波特率无关 |
| `g_radar_pin_low = 0x2CA640` | PA3 被大量采样为低；单值无法区分"正常帧流量"与"线路常低"，需要按秒统计才能判读 |

**调试手段本身失效（本次放弃的直接原因）**：本板没有串口输出，只能靠 Keil Watch 抄单值，
而结构体/数组/函数表达式都不能取（现场已明确要求）。"按秒统计 + 多标量交叉判读"需要人工抄 5~7 个数字、
还不保证同时刻，**现场不可行**。以后再碰这类问题，必须先解决可观测性
（例如把诊断集中到一块能被调试器整块导出的内存区，或临时飞线出一个调试串口），否则不要开工。

**保留下来的知识**：分频/过采样的取舍（§5.2 的表）与"SDK 例程用 \`USART_CLK_DIV64\` 只适用于单档低波特率"
这一结论，已写进 \`radar_cfg.h\` 的注释，避免以后重复踩坑。

## 6.1 追加实测数据（叫停之后拿到的，反而把问题指死了）

用户在诊断版 \`7a9d206\`（模块由 APP 设为 9600、驱动上电即 9600、不改档不发命令）上实测：

| 变量 | 实测 | 判读 |
| --- | --- | --- |
| \`g_radar_low_pct\` | **13**（%） | PA3 有 13% 时间为低。9600 下 23 字节帧占线 24ms，若模块按 ~10Hz 上报，低电平占比 ≈ 0.5×24/100 = 12% —— **与『模块正以 9600、约 10Hz 正常上报』完全吻合** |
| \`g_radar_dma_fill\` | **15**（字节/秒） | RX DMA 每秒只搬走约 15 字节，而按上面推算线上应有 ~230 字节/秒 |
| \`g_radar_to_hz\` | **0** | 空闲超时中断**一次都没来**（这条上抛路径从未工作） |
| \`g_radar_win_hz\` | **0** | 窗口(256B)从未填满（每秒才 15 字节，本来就填不满） |
| \`g_radar_bps\` | **0** | 环形缓冲每秒 0 字节 → \`s_reports\` 必然恒 0 |
| \`g_radar_rx_err\` | **0** | 无帧错/校验错/溢出中断（注意：这条中断路径本身没单独验证过，不能反推『波特率一定对』） |
| \`g_radar_poll_hz\` | **204509** | 主循环 ~205kHz，说明上面的采样足够密、数字可信；也解释了过去 \`pin_low=0x2CA640\` ≈ 13%×205k×110s |

**由这些数字得到的结论（比 §6 更进一层，且改写了 §6 的部分判断）**：

1. **波特率/分频确实无关**：BRR 回读正确，且 13% 占空比与『9600 + ~10Hz 上报』的推算吻合。
2. **也不是『运行时换档』**：这一版上电就是 9600，全程没有换过档、没有发过命令。
3. **卡点在接收链**：RX DMA 每秒只搬 ~15 字节 —— 既到不了窗口满(256)，空闲超时中断又从不触发，
   于是字节永远进不了环形缓冲，\`s_reports\` 恒 0。这同时解释了『运行时 \`rx_bytes\`=0、Keil 暂停再恢复变 \`0x100\`』：
   CPU 停住时 DMA 继续攒，攒够 256 才出一次 TC。
4. **最可疑的结构问题**：这套接收是『256B 窗口 + AOS LLP 重装 + 靠中断上抛』，其中
   **空闲超时上抛路径（\`to_hz\`）从来没工作过**，而 460800 下窗口 ~23ms 就填满，
   所以『只有窗口满这条路上抛』在高波特率下完全够用 —— **低波特率只是把这颗雷暴露出来了**。
   \`fill\` 只有 15 也提示：字节可能一直被某个周期(~70ms)事件重装窗口冲掉，攒不起来。

> 由此看，§6 里『与固件无关、先放弃』的结论要修正为：**模块与波特率都没问题，问题在我们自己的接收架构**；
> 当时的『没法调试』指的是诊断手段（手工抄单值），不是问题本身没法解决。

## 7. 调试方法规范（2026-09-14 定，今后强制执行）

### 禁止

**再为调试往 Keil Watch 加全局变量 / 快照结构体。**
本板没有连电脑的串口，Watch 只能一个一个手抄单值：结构体、数组、函数表达式都取不出来；
『按秒统计 + 多标量交叉判读』在现场抄不完、也对不齐时刻 —— 现场结论原话：**没法调试**。
（`g_radar_dbg` 快照、以及 `g_radar_low_pct` / `to_hz` / `win_hz` / `dma_fill` / `bps` / `pin_low` 这套秒统计，
都是这条错误路线的产物，**已全部删除**。）

### 需要观测时，只允许这三种方式

1. **肉眼可见通道**：板上 LED（R/G/B、Radar_LED）与蜂鸣器。把结果编码成『闪几下 / 长亮 / 短闪』，不接调试器就能判读。
2. **既有上行通道**：STM32 每 20ms 查询一次，报警板回 32B `gpio_pdu`（`Rad_Status[8]` / `Alarm_Done[8]` / `GPIO[10]`）。
   要观测的量塞进这个已定义帧（或复用已有字段），而不是新开 Watch 变量。
3. **调试器整块导出**：确实要看内存，就用 Memory 窗口/命令行**一次性导出一整块**，而不是往 Watch 里逐个添加变量；
   临时观测用的代码**用完即删**，不进主干。

### 判断标准

一个诊断方法如果要求『人坐在 Keil 前逐个抄数字』，就是不合格的方法 —— 换方法，不要开工。

## 8. 结论（2026-09-14 晚，现场验证通过）

**自适应打通**：模块**真断电重启**后读数为 `g_radar_lock = 1`、`g_radar_baud = 460800`、`g_radar_comm = 0x301`
（bit0 = 460800 档收到字节；0x100 = 解出过合法上报帧；0x200 = 最近 1 秒内仍在收 = **正在正常通信**）。

### 8.1 最终定型的接收方案（三处根因，全部已改）

| # | 根因 | 修法 |
| --- | --- | --- |
| 1 | **分频写死**：写死 `DIV4` + 8 倍过采样时 9600 需要分频比 324 > 255 → `USART_SetBaudrate()` 返回错误**且不写 BRR**，端口静默停在旧波特率 | 分频**随波特率算**：`(baud < 115200) ? DIV64 : DIV1`（照抄扫描台主板同款 HC32F460 的量产写法） |
| 2 | **交付路径不成立**：原『256B DMA 窗口 + AOS/LLP 重装 + 空闲超时中断上抛』中，空闲超时上抛**从未工作过**；高波特率下窗口 20ms 填满掩盖了它，低波特率下窗口 1 秒以上才填满、RX DMA 每秒只搬 15 字节 | 接收改**逐字节 RI 中断**（SDK `usart_uart_int` 同款：RI/EI 分开注册、错误中断读 RDR 并清 PE/FE/ORE、统一 `USART_FuncCmd(RX|TX|INT_RX)`）；**换档不再碰 DMA** |
| 3 | **吞返回值**：`(void)USART_UART_Init/SetBaudrate(...)`，失败无人知 | 检查返回码，结果放 `radar_port_baud_ok()`；`CKOutput` 改为 DISABLE（参考实现『时钟不输出』） |

### 8.2 现场教训：模块卡配置态必须断电重启

LD2410C **一旦处于配置态（0x00FF 之后没被 0x00FE 收尾）就完全停止上报**，线上整段空闲高电平 →
**8 档全程零字节**（`g_radar_comm = 0`）。纯监听方案**无法自救**：不发东西 → 模块不出来 → 收不到帧。
本次 `comm = 0` 就是这个原因，**真正断电重启**（不是 APP 里的重启命令）后立刻恢复。

### 8.3 事实修正（模块侧，待客户/APP 侧确认）

手机 APP『恢复出厂设置』+ 断电重启后，模块**仍在 460800 上报**（`comm = 0x301`，解出的是合法帧而非乱码），
与『LD2410C 出厂默认 256000』的文档说法不符 —— 该说法可能来自其它型号/版本文档。
APP 设 256000 为何不生效（写入失败，或恢复出厂不改 UART 波特率）**属模块/APP 侧问题**，需另行确认；
固件口径是**只跟随、不写模块**（`RADAR_BAUD_TARGET = 0`），模块在哪一档固件就锁哪一档，不卡功能。

### 8.4 现场 Watch 规范（收敛为 3 个单值，不许再加）

`g_radar_lock`（1 已锁定）、`g_radar_baud`（锁定到的波特率）、`g_radar_comm`（位图：bit0..7 各候选档是否收到过字节，
顺序同 `RADAR_BAUD_TABLE`；0x100 曾解出合法帧；0x200 最近 1 秒仍在收）。
读法：`0` = 模块没发/接线/卡配置态；`0x08` = 模块在 9600；`0x301` = 460800 正常通信。

### 8.5 低波特率打通（现场实测，2026-09-14 夜）

模块设为 **9600** → `g_radar_lock = 1`、`g_radar_baud = 9600`、`g_radar_comm = 0x130708`（1246984）：
bit3（9600 档）收到字节并解出合法帧；`0x100/0x200/0x400` 全置位；高位 `0x13` = 19 = BRR 整数分频,
即 <115200 走 DIV64（C = 1.5625MHz，`C/(B*8) = 20.345 → 19`）—— **与规则完全一致**。

两档现场记录对照：

| 模块波特率 | 锁定档 bit | 分频 | BRR 整数 | `g_radar_comm` |
| --- | --- | --- | --- | --- |
| 256000 | bit1 | DIV1 (C=100MHz) | 47 | `0x2F0703` |
| 9600 | bit3 | DIV64 (C=1.5625MHz) | 19 | `0x0A130708`（bit24..31=0x0A ⇒ **帧率 10 Hz**） |
| 38400 | bit5 | DIV64 (C=1.5625MHz) | 4 | `0x04073E` |
| 115200 | bit2 | DIV1 (C=100MHz) | 107 (0x6B) | `0x6B0707` |
| 230400 | bit7 | DIV1 (C=100MHz) | 53 (0x35) | `0x0A3507F7`（bit24..31=0x0A ⇒ **帧率 10 Hz**） |
| 460800 | bit0 | DIV1 (C=100MHz) | 26 (0x1A) | `0x1A0701` |

**六档实测（9600/38400/115200/230400/256000/460800）的 BRR 整数分频与公式预测全部一致**：
DIV64 档 9600→19、38400→4；DIV1 档 115200→107、230400→53、256000→47、460800→26。
锁定永远发生在模块真实那一档（bit 与 `g_radar_baud` 一致）。仅剩 19200、57600 未单独实测（同属 DIV64 段）。

结论：**『客户用 APP 随便改波特率，固件自动跟随』这一口径已在两个极端档上验证通过**。

## 9. 追加（多口化第 3 步现场）：38400 收不到的真正原因在**硬件**

> 起因：三路雷达多口化（第 3 步）后，雷达3 口（USART3/PB14/PB15）**只有 9600 / 19200 能自适应成功，38400 及以上一律失败**。
> 本节记录定位过程与结论 —— **这是本文件里第一次把「收不到」的原因落到硬件上**，不是驱动、不是分频、不是波特率表。

### 9.1 现象与读数

模块用手机 APP 设为 38400、模块与主板都断电重启后：

| 读数 | 值 | 解码 |
| --- | --- | --- |
| `g_radar_lock[2]` | 0 | 未锁定 |
| `g_radar_baud[2]` | 256000 | 回落值（`RADAR_BAUD_FALLBACK`） |
| `g_radar_comm[2]` | `0x002F05FF` | 位图 `0xFF`（八档都收到过字节）+ `0x100` 曾解出帧 + `0x400` BRR 写入确认；帧率 0、`0x200`=0 |

### 9.2 排除固件（三条硬证据）

1. **19200 与 38400 走的是同一个分频**：`radar_pick_clk_div()` 只按 `< 115200` 二分，
   所以 9600/19200/38400/57600 都是 **DIV64（C = 1.5625MHz）、误差同为 0.136%** ——
   **固件里不存在能切在 19200 和 38400 之间的判据**。

   | 波特率 | 分频 | bit 时间 | BRR 整数 | 实际波特率 | 误差 |
   | --- | --- | --- | --- | --- | --- |
   | 9600 | DIV64 | 104.2 µs | 19 | 9613 | 0.136% |
   | 19200 | DIV64 | 52.1 µs | 9 | 19226 | 0.136% |
   | 38400 | DIV64 | 26.0 µs | 4 | 38452 | 0.136% |
   | 57600 | DIV64 | 17.4 µs | 2 | 57475 | 0.217% |

2. **口2 在 9600/19200 上是好的**：`lock=1`、帧率 10 Hz、BRR 指纹正确 ⇒ 引脚复用（Func_Grp2 + 32/33 = USART3_TX/RX）、
   USART3、FCG1_PERIPH_USART3、INTC 登记 / NVIC / 跳板、按口分帧器、探测状态机**在口2 上全部被实测证明可用**。
   唯一剩下的变量只有「线上的 bit 速率」。

3. **口0/口1 用同一份 `radar_port.c`** 分别跑通 460800（2.2 µs/bit）与 115200 —— 一份代码不可能对某个口号只在 38400 以上失效。

### 9.3 判据：怎么把「波特率选错」和「信号带宽不够」分开

> `RADAR_BAUD_LOCK_FRAMES = 1`，模块恒定 **10 Hz** 上报，每档监听窗口 `RADAR_PROBE_LISTEN_MS = 300ms` 内约 **3 帧**。
> ⇒ **只要正确那一档的信号是干净的，一轮扫描（8 档 × 300ms = 2.4s）内必然锁定 —— 3 帧里有 1 帧干净就够。**
> ⇒ **正确档扫到了却不锁 ⇒ 不是波特率没选对，而是该波特率下的信号本身不合格。**

### 9.4 量化窗口（一阶 RC）

UART 在 bit 中点采样，要求信号基本建立（取 2.3τ ≈ 90%）：

| | bit 时间 | 采样点 | 要求 |
| --- | --- | --- | --- |
| 19200 能过 | 52.1 µs | 26.0 µs | 2.3τ < 26 µs ⇒ τ < 11.3 µs |
| 38400 过不去 | 26.0 µs | 13.0 µs | 2.3τ > 13 µs ⇒ τ > 5.7 µs |

⇒ **该路 RC 时间常数约 6 ~ 11 µs**，对应元件：

| 串联电阻 R | 需要并联的电容 C |
| --- | --- |
| 100 Ω | 60 ~ 110 nF |
| 470 Ω | 12.8 ~ 23 nF |
| 1 kΩ | 6 ~ 11 nF |
| 4.7 kΩ | 1.3 ~ 2.3 nF |
| 10 kΩ | 0.6 ~ 1.1 nF |

正常的 ESD/滤波电容应在 **100 pF 量级**（τ ≈ 100 ns ~ 1 µs），对 460800 也毫无影响。
**贴成 nF 量级就正好落进上面这个区间。**

### 9.5 结论与验证

**根因：雷达3 口 RX 线（PB15）上一颗对地滤波电容偏大。**

**验证：拆掉该电容后，三路雷达 460800 全部自适应通过。**

排障顺序（供下次复用）：

1. 先看三个读数 → 用 §9.3 的判据区分「波特率选错」与「信号不合格」（也可用 `radar_multiport_todo.md` §8.3 的速查表）；
2. 对调模块 + 线材，看故障**跟不跟着走** —— 跟着走 = 模块/线；留在原口 = 主板该通道；
3. 拿**已知能跑 460800 的口**（本板是口0）作基准，逐项对比该路的**对地电容 / 串联电阻 / 接插件 / 共地**；
4. 最快验证：**直接把那颗电容摘掉再看**（台面验证摘掉无害；量产要按正确容值装回，如果它是 ESD 防护网络的一部分）。

> 教训：**「低波特率能通、高波特率不通」且两个波特率共用同一套分频/误差时，先怀疑线上的 RC，不要再翻驱动。**
  §6 当年在 9600 上放弃时，把「接收链」当成了唯一方向 —— 这一次证明至少有一部分「收不到」确实是模拟层的事。

## 10. 追加（2026-09-15）：模块卡在配置态，UART 层面能不能自救 —— 两次受控实验

> 起因：多口化后做**逐口参数配置**，现场出现过口1/口2 的模块被卡在配置态（只能断电救）。
> 问题：除了断电，串口层面有没有自愈手段？候选是「重扫时补发**裸 0x00FE**」还是「发 0x00A3 重启」。
> 手册 2.2.1 写着「对雷达下发的**任何其他命令**必须在此命令下发后方可执行，否则无效」，
> **并没有豁免 0x00FE** —— 所以只能实测。实验用 `g_radar_comm` 的 **bit11..15** 编码结果，不新增 Watch 变量。

### 10.1 手册依据（2026-09-15 从 PDF 提取的原文）

- **2.2.1 使能配置命令**（`0x00FF`，命令值 `0x0001`）：
  「对雷达下发的任何其他命令必须在此命令下发后方可执行，否则无效。」
- **2.2.2 结束配置命令**（`0x00FE`，命令值：无，返回值：2字节ACK状态）：
  「结束配置命令，**执行后雷达恢复工作模式**。如需再次下发其他命令，需要先发送使能配置命令。」
  发送数据 `FD FC FB FA 02 00 FE 00 04 03 02 01`
- **2.2.11 重启模块**（`0x00A3`）：「模块收到此命令，将会在应答发送完成后自动重启。」
- **2.4.1**：「向雷达发送任何其他命令前，开发者需先发送『使能配置』命令，然后在**规定时间内**发送配置命令。」
  —— 「规定时间」手册**没给数值**。
- **2.2.3**：最大运动/静止距离门配置范围 **2~8**，无人持续时间 **0~65535 秒**，「参数值若不在范围失败」。
- **表 7 出厂默认值**：门 8/8、无人持续时间 5、波特率 256000、分辨率 0.75m。

### 10.2 实验 1：给**正常态**模块裸发 0x00FE

做法：口0 **锁定且稳定收帧**后等 5 秒，只发一帧裸 `0x00FE`（不带 `0x00FF`），之后什么都不做。

结果 `g_radar_comm[0] = 169484035 = 0x0A1A1F03`：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| 实验码 bit11..15 | **3** | 回 ACK 但 **status≠0**（模块判「无效」） |
| `0x200` 最近1秒仍在收 | 1 | **正在正常通信** |
| bit24..31 帧率 | 10 Hz | **正常** |
| 位图 / BRR 指纹 | 与对照口完全一致 | **报文流零影响** |

口1/口2（对照）全程 `0x0A1A0703`（实验码 0）→ 实验只影响口0，**没有串到别的口**。

**结论**：裸 `0x00FE` 给**正常态**模块 → **被判无效，但不打断上报**（安全）。
这坐实了手册 2.2.1 的「否则无效」**确实也管 `0x00FE`**。

### 10.3 实验 2：给**卡在配置态**的模块裸发 0x00FE

做法：口0 锁定且稳定收帧后 → 发 `0x00FF` 且**故意不发 `0x00FE`**（把模块**故意弄哑**）→ 等 10 秒
（模拟「卡了很久」）→ 发一帧**裸 `0x00FE`** → 观察帧率是否恢复。

结果 `g_radar_comm[0] = 169486083 = 0x0A1A2703`：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| 实验码 bit11..15 | **4** | 回 ACK 且 **status=0**（模块**接受**） |
| `0x200` 最近1秒仍在收 | 1 | **正在正常通信** |
| bit24..31 帧率 | 10 Hz | **已恢复上报** |

**结论**：裸 `0x00FE` 对**卡在配置态**的模块 → **被接受，并恢复上报**（有效）。

> 实现细节（很重要）：本口必须**冻结失联兜底重扫**。否则模块一哑，链路监控 3 秒后就把波特率
> 扫走了，后面那一帧会发在**错档**上，实验直接失效。

### 10.4 两次实验合起来得到的结论

| 模块状态 | 裸 `0x00FE` 的结果 | 上报 |
| --- | --- | --- |
| **正常态** | ACK 但 status≠0（判无效） | **不受影响** |
| **配置态** | ACK 且 status=0（接受） | **恢复上报** |

**手册 2.2.1 那句「否则无效」只在模块「不在配置态」时生效；模块一旦卡在配置态，`0x00FE` 正是它的收尾命令。**

也就是说：**`0x00FE` 只在需要它的时候生效** —— 这是我们能拿到的最好结果。安全性（不打扰正常模块）
与有效性（能救卡死的模块）同时成立。

### 10.5 落地：重扫急救包

`radar_cfg.h` 新增 `RADAR_PROBE_FAILSAFE`（`0` 关闭 / `1` **只有重扫发**（当前默认） / `2` 上电首次也发）；
`radar_switch_baud()` 换到每一档之后补发一帧裸 `0x00FE`（`radar_probe_failsafe()`，见 `radar.c`）。

> ⚠️ **2026-09-15 现场回归后补了门控**：这一版刚落地时是"只要重扫就每档都发"，结果撞坏了客户 APP 的配置会话（见 §10.8）。
> 现在 `radar_probe_failsafe()` 里还有**第二道**条件 —— 该口必须已经**长时间收不到任何字节**
> （`RADAR_FAILSAFE_SILENT_MS`，默认 **30 s**）才真的发出去。下面这些取舍仍然成立，只是多了一道闸。

- **为什么每档都发**：模块卡住时不知道它在哪一档，只能在每个候选波特率上各补一帧；
  发错档就是乱码，魔术字（帧头/帧尾）也拦得住，无害。
- **为什么不发 `0x00FF`**：它才会把模块**推进**配置态，是现场明令禁止的；`0x00FE` 没有这个语义。
- **时序**：必须在 `radar_port_set_baud()` 之后（换档要求 TX 空闲）；一帧 11 字节 @9600 只要 11.5ms，
  而本档监听窗口 `RADAR_PROBE_LISTEN_MS = 300ms`，发完立刻听得过来。
- **`=1` 与 `=2` 的取舍**：`=1` 时上电首次探测仍是纯监听（符合现场口径的字面）；
  `=2` 还能救「上一次遗留的卡死模块」，且实测无害，但要现场点头才改。

### 10.6 两条伴生的实现修正（同一次实测暴露）

1. **`radar_cfg_cmd()` 无条件发 `0x00FE`**。原来在 `0x00FF` 失败时直接 `return`，结束帧就永远发不出去 ——
   但 `0x00FF` 的 **ACK 丢了不等于模块没进配置态**，于是模块被留在配置态、现场只能断电。
2. **参数配置每拍只推进一个口**（轮转下标）。命令事务是**阻塞**的（一笔最坏 3×200ms），三个口同一拍
   会把彼此的雷达泵与链路监控**饿死** —— 现场实测口0 排在前没事、口1/口2 的 `0x00FF` 因此超时。
   顺带：`radar_cfg_cmd()` 收尾时把该口的**链路监控窗口整体后移**，免得「配置期静默」被失联兜底判据
   误判成断链而触发重扫。

### 10.7 参数合法性：前置校验（手册给了范围就该校验）

手册明确了范围，所以写之前先在本地拦掉，**连帧都不组**：

| 接口 | 命令 | 范围（手册） |
| --- | --- | --- |
| `radar_set_max_gate_port()` | `0x0060` | 运动/静止距离门 **2~8**（无人持续时间 uint16 天然满足 0~65535） |
| `radar_set_sensitivity_port()` | `0x0064` | 门 **0~8**、灵敏度 **0~100** |
| `radar_set_resolution()` | `0x00AA` | **0/1** |

另外在 `radar_cfg.h` 加了**编译期**检查：`RADAR_PARAM_MAX_MOVE_GATE` / `MAX_STILL_GATE` 越界直接 `#error`，
写错宁可编不过，也别把非法参数发给模块。

## 11. 现场回归（2026-09-15）：急救包撞坏客户 APP —— 加门控 + 参数配置默认关

**现象**：急救包（`RADAR_PROBE_FAILSAFE = 1`）落地后，现场用手机 APP 配模块报
**「设置距离门灵敏度失败 返回码：6401」**，而且**时好时坏**。

**根因（两条，都不是 `0x00FE` 本身的问题，而是"什么时候发"的问题）**：

1. **急救包发的时机太随意**。当时只要「本轮是重扫」就**每一档**补一帧裸 `0x00FE`，
   而重扫的触发条件是链路失联兜底 —— **3 秒**收不到字节就扫（`RADAR_LINK_SILENT_MS`）。
   APP 配模块时模块同样停止上报，但 APP 的命令/ACK 一直在线上跑，**人一停顿超过 3 秒**，
   兜底重扫就开跑，急救包当场插进 APP 的事务 —— APP 的 `0x00FF` 会话被我们的 `0x00FE` 提前收尾，
   下一条命令（`0x0064`）被模块判「无效」→ 报错。
   **"时好时坏"正是因为"人停顿多久"是随机的。**
2. **参数自动配置在运行时一直开着**（当时 `RADAR_PARAM_EN = 2`），它自己也在跟模块做
   `0x00FF -> 命令 -> 0x00FE` 事务，跟 APP 抢同一个模块。

> 证据强度说明：本板**没有调试串口**，抓不到"我们那一帧与 APP 命令相撞"的时序波形。
> 上面第 1 条是从「现象随机 + 触发条件精确等于 3 秒阈值 + 关掉就正常」反推的结论，
> 不是直接观测 —— 记在这里以免以后被当成实测数据引用。

**改法**：

| 改动 | 位置 | 说明 |
| --- | --- | --- |
| 急救包加**门控** | `radar_probe_failsafe()` + `RADAR_FAILSAFE_SILENT_MS`（30 s） | 该口连续 ≥30 s 收不到**任何字节**才允许发 |
| 参数自动配置**出厂默认关** | `RADAR_PARAM_EN = 0` | 要配参数时手动改 `2`，逐口读数确认后改回 `0` |

**为什么门控选"长时间全静默"，而不是别的判据**：

- 卡在配置态的模块是**彻底静默**的（连 ACK 都不回，见 §10.3 里那 10 秒零字节）→ 门控必然放行，**该救的照样救**；
- APP 会话期间线上**一直有字节**（命令 + ACK）→ 门控不放行，**插不进去**；
- 阈值取 30 s：人的一次 APP 操作中间停顿几秒很常见，但"30 秒一个字节都没有"基本排除了人的会话。
  调大更保守、调小更激进 —— 只动一个宏。
- 判据用的是 `s_link_last_rx_ms`：链路监控每秒结算时刷新，`radar_cfg_cmd()` 收尾也会把它推到"现在"，
  所以**本固件自己的配置事务刚做完时同样不会立刻放行**。

**残留风险（说清楚，不掩盖）**：如果人真把 APP 开着 30 秒不碰（比如放下手机去干别的），
门控仍会在第 30 秒放行。代价是"APP 那一次要重来"，不是永久损坏 ——
门控是把概率压到可接受，**不是数学上不可能撞**。

**怎么验证**：

1. 上电正常跑：`g_radar_comm[p]` 的位图 / `0x200` / 帧率**照旧**（门控只在重扫路径上，不碰正常链路）；
2. 人为把模块弄哑（发裸 `0x00FF` 且不收尾，做法见 §10.3）→ 等 ≥30 s → 看该口是否**自己恢复上报**（锁定 + 10 Hz）；
3. APP 配置：全程不应再出现 6401。

**结论**：`0x00FE` 的定位没变 —— 它仍然是"只在需要它的时候生效"的收尾命令（§10.4）；
变的是**我们发它的门槛**：从"一重扫就发"改成"长时间全静默才发"。
