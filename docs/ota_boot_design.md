# Boot/OTA 设计 —— A/B 双槽即运行区、选择器标志、无搬运（设计稿 v0.1）

> 状态：设计稿，未改动任何固件代码。仓库基线 v0.1.0（HEAD 含 MVP 三笔提交）保持。
> 范围：Linux 主机经 STM32F0 中继分发，对 STM32F0 / HC32F460 的串口 OTA 升级；两 MCU 共用同一套协议与 Boot 框架（各自 HAL 不同）。

## 1. 背景与目标

- 需求：通过 Linux 主机分发，远程升级 STM32 中继板与各 HC32 报警板固件；
- 硬指标：升级过程任何时刻掉电/中断/新固件无法启动，设备都不变砖，且可自动回退；
- 现状固件体积（Release、去调试信息）：STM32 净 Flash ≈9.98KB（256KB 的 3.9%）、RAM 16.88/32KB；HC32 ≈25.46KB（512KB 的 5.0%）、RAM 7.5KB → 空间余量充足，容量不是问题，流程安全才是问题。

## 2. 核心模型（本设计的基本盘）

1. A/B 双槽即为 App 运行区：新固件写入“非活动槽”，写完只翻转一个选择器标志，Boot 按标志直接跳到 A 或 B 运行；
2. 不做任何“搬运/拷贝覆盖”（暂存槽→固定运行区的两段式单槽模型被否决：搬运中断即损坏运行区=变砖）；
3. 选择器标志是唯一真值：版本号不参与选槽（见 §6）；
4. RAM 只做页级缓冲（1KB），不做整包暂存——STM32F030 当前 RAM 已用 16.88/32KB，放不下自身整包镜像；
5. 下载期页粒度擦写非活动槽（每页擦写停顿仅数 ms，放入 10ms 心跳空窗），运行区永不触碰；
6. Boot 区永不自擦、永不参与槽切换以外的写操作；App 与升级流程无权写 Boot。

## 3. 内存布局（默认值，可调）

### STM32F030CC（256KB Flash，基址 0x08000000）

| 区 | 地址 | 大小（默认） |
| --- | --- | --- |
| Boot | 0x08000000 | 16KB |
| 槽 A（App 运行区） | 0x08004000 | 64KB |
| 槽 B（App 运行区） | 0x08014000 | 64KB |
| 保留/扩容 | 0x08024000 | ~104KB |
| 参数/选择器标志区（双份） | 0x0803F000 | 4KB |

### HC32F460xE（512KB Flash，基址 0x00000000）

| 区 | 地址 | 大小（默认） |
| --- | --- | --- |
| Boot | 0x00000000 | 32KB |
| 槽 A（App 运行区） | 0x00008000 | 128KB |
| 槽 B（App 运行区） | 0x00028000 | 128KB |
| 保留/扩容 | 0x00048000 | ~192KB |
| 参数/选择器标志区（双份） | 0x0007E000 | 8KB |

## 4. 槽镜像头（每个槽首部固定字段）

| 偏移 | 字段 | 长度 | 说明 |
| --- | --- | --- | --- |
| 0 | Magic | 4B | 固定魔数，区分空/错槽 |
| 4 | Version | 4B | 主.次.构建（仅展示/防呆，不参与选槽） |
| 8 | ImageLen | 4B | 镜像字节数 |
| 12 | CRC32 | 4B | 整包（含头）CRC32 |
| 16 | TargetSlot | 1B | A 或 B（防错槽运行） |
| 17+ | 保留 | - | 后续可加日期/描述 |

Boot 跳槽前校验：Magic 正确 → ImageLen 在合法区间 → 整镜像 CRC32 一致 → TargetSlot 与槽位一致。

## 5. Boot 启动流程与选择器标志

选择器标志区独立放置，双份存储 + 各自 CRC；每槽状态字：EMPTY / RUNNABLE / TRIAL(试运行) / FAILED。

复位 → 读双份标志(各自CRC)
  ├─ 双份一致且有效: 选中槽 RUNNABLE/TRIAL → 校验该槽头+整CRC
  │      ├─ 通过 → 状态置 TRIAL, 跳转该槽, 开“新固件确认窗口”(默认3s)
  │      └─ 失败 → 该槽置 FAILED(计数+1), 切另一槽(回到流程头)
  ├─ 双份不一致/损坏 → 按 A→B 顺序取第一个 Magic+CRC 全过的槽运行
  ├─ 全部槽无效 → 停留 Boot(等待 OTA / 上报 Linux) —— 不跳任何槽=不砖
  └─ 跳转后新固件未在窗口内喂狗(起不来) → 该槽 FAILED+1, 复位切另一槽;
      同槽连续失败达上限(默认2次) → 不再自动试, 上报 Linux 等待人工/重发

## 6. 为什么版本号不用于选槽

| 情形 | 若用版本号比较 | 用选择器标志 |
| --- | --- | --- |
| 两槽版本相同（重刷同版/改配置发布） | 无法区分 | 明确选刚下载的槽 |
| 新版本起不来 | 版本高→每回都跳坏槽→一直砖 | 试运行失败→自动回滚 |
| 人为降级发布 | 版本低→永不选中 | 下载流程明确写目标槽 |
| 某槽头损坏/半擦 | 读到假版本误判 | 先过 Magic+CRC，坏了不参与选择 |
| 双份标志半写 | — | CRC 判无效→顺序扫描兜底 |

版本号职责收敛为：Linux 读取/展示当前运行版本、下载前防呆（新版本≤当前版本时提示/中止）、日志记录。

## 7. 按槽分别编译两份（两槽链接不同偏移）

- 槽 A 与槽 B 是两个独立编译产物（同一源码，链接脚本偏移不同：A 起点 vs B 起点）；
- STM32F030（M0，无 VTOR）：App 在非 0 偏移启动必须把向量表搬到 SRAM 底部并用 SYSCFG_CFGR1.MEM_MODE 重映射 0 地址（A/B 各自实现），Boot 跳转前也要正确设置；
- HC32F460（M4F，有 VTOR）：App 启动早期写 SCB->VTOR = 本槽基址即可；
- 禁止“同一份镜像运行时自适应基址”：M0 无 VTOR，向量表为链接期写死，做不到——发布流程固定为两步构建（产 A 镜像 + 产 B 镜像），镜像头 TargetSlot 字段防止错槽烧录/运行。

## 8. 升级全流程（无搬运步骤）

Linux → STM32(中继) → 目标: 自身(STM32) 或 某通道 HC32 (STM32 透明转发, 460800 RS485)
  1 握手: ENTER_BOOT / GET_INFO(当前版本/容量/槽状态)   （含防呆: 新版本≤当前则中止）
  2 擦除非活动槽(页粒度), 边擦边报进度
  3 分块下载: WRITE_CHUNK(每块≤1KB, 带序号+CRC) → ACK/NACK, 写满一页即擦写该页, 页写后回读校验
  4 整包完成 → VERIFY(整镜像 CRC32 重算比对)
  5 ACTIVATE: 写“目标槽 RUNNABLE”标志(双份+CRC)  ← 唯一破坏性点, 对另一槽零影响
  6 复位 → Boot 读标志→校验→跳新槽(TRIAL)→ 新固件 3s 内喂狗确认 → 状态转 RUNNABLE

### 掉电矩阵（任何时刻掉电均不砖）

| 掉电时刻 | 结果 |
| --- | --- |
| 非活动槽擦/写到一半 | 该槽 CRC 不过 → 继续跑另一槽，可整包重传 |
| 标志写了一半 | 双份+CRC 判“未就绪” → 跑原槽 |
| 新固件启动崩溃/超时 | TRIAL 失败计数 → 自动回原槽并上报 Linux |
| 两槽都被写坏（出厂前/异常双写） | 停留 Boot 等待恢复（Boot 自身永不被写） |

## 9. 协议与中继（后续细化，先定框架）

- 独立帧头族（建议 0xA5 开头，与现有 0xFF alarm_pdu / 0x55 GPIOHEAD 不冲突）：ENTER_BOOT / GET_INFO / ERASE / WRITE_CHUNK / VERIFY / ACTIVATE / ABORT / 应答帧；
- 命令/状态机源码两端共用（同一 .c/.h 编译进两个工程，HAL 差异隔离在刷写驱动层：erase_page / write_page / verify 回调）；
- 中继模式：目标为 HC32 时，STM32（App 或 Boot）按通道把 OTA 帧透明转发到 COM2..6 并把应答原路返回 Linux；Boot 阶段 STM32 自身也要具备该中继能力，否则 Linux 无法穿透升级 HC32；
- 半双工 RS485：保持“主站主导、目标应答”握手（与 GPIOHEAD 轮询同构），天然不撞线；
- 波特率：STM32 IPC=115200，HC32 RS485=460800，协议层不感知。

## 10. 关键工程约束清单（实现时必须满足）

- Boot 区永不自擦/自升级；App 与升级流程无 Boot 区写权限；
- 下载期页擦写放 10ms 心跳空窗/关中断短窗；擦写期间挂起 RS485 上行心跳与 50ms 轮询（下行接收仍由 FIFO/中断缓冲），避免时序互踩；
- 每页写后回读校验，失败即中止并上报（可重传该页）；
- 整包传输失败策略（默认）：整包重传，不做断点续传（验证版从简）；
- 升级期间禁用/配合看门狗：Boot 窗口用独立短看门狗；App 正常喂狗节奏不变。

## 11. 默认参数表

| 参数 | 默认值 |
| --- | --- |
| 分块大小 | ≤1KB（=1 页擦写粒度） |
| 校验 | CRC32（整包 + 每块） |
| 新固件确认窗口 | 3s（Boot 看门狗） |
| 自动回退上限 | 同槽连续失败 2 次后不再自动试 |
| 断点续传 | 不支持（整包重传） |
| Boot 大小 | STM32 16KB / HC32 32KB（默认） |
| 槽大小 | STM32 A/B 各 64KB；HC32 A/B 各 128KB（默认，余量可扩） |

## 12. 开放问题（下一轮细化）

- Linux 侧是否有既定 OTA 帧格式/流程约束；
- 是否需要保留“上一版”能力（多版本回退，需 N+1 槽位或 Linux 侧存历史包）；
- Boot 本身升级路径（出厂后是否需要？建议只在产线用调试器更新，远程不做）；
- 升级期间是否允许报警业务照常（默认：允许，下载不影响 A 运行，仅切换瞬间复位）；
- 每块 HC32 的 DeviceID/通道号在 OTA 命令里的编址方式（与现有 AntID/通道映射衔接）。
